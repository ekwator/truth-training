# ATPP: Research & Architecture Decisions (Phase 0)

## 1. Содержание и границы задачи
Anonymous Trust Propagation Protocol (ATPP) предназначен для анонимной рассылки зашифрованных событий по децентрализованной peer-to-peer сети без раскрытия отправителей/получателей и без прямых подтверждений успешной доставки. Границы: протокол фокусируется на обеспечении базовой приватности, спама-устойчивости, доверительной обратной связи (Emergent Trust Factor, ETF) и адекватного пользовательского UI для trust-feedback по каждому событию.

## 2. Основные архитектурные решения
- **Антиспам/лимитирование**: встроено лимитирование частоты публикации/ретрансляции событий на каждом узле (default: 1/30s, настройка параметра допускается). Попытка превышения лимита приводит к временной блокировке публикаций.
- **Приватность/анонимность**: сквозное шифрование, запрет хранения/передачи любых идентификаторов отправителя/получателя, отсутствие специальной маршрутизации или mix-net; intersection protection реализуется только базовыми методами (архитектурный компромисс — см. clarifications).
- **Emergent Trust Factor (ETF)**: должен рассчитываться и отображаться для каждого события непосредственно в пользовательском UI (см. FR-014), с автообновлением.
- **TTL и UI**: если событие не было отражено обратно источнику до истечения TTL, UI обязан явно информировать пользователя о том, что «событие не было подтверждено/доверено» (см. FR-015).
- **Конфигурируемость лимитов**: лимит публикаций должен быть настраиваемым через параметры сети/администрирования, чтобы адаптироваться под разные размеры и топологии P2P-сети.

## 3. Рационализация выбора
- **Почему rate-limiting, а не депозиты/оплаты/доверительная фильтрация?** Минимальные издержки внедрения, хорошая объяснимость для любых масштабов peer set, не осложняет bootstrap.
- **Почему не mix-net и не усиленные приватные реле?** Повышение устойчивости к intersection attacks отложено для следующего релиза по причине роста сложности и стоимости поддержки. Основываемся на сквозном шифровании, отсутствии маршрутизации и анонимности payload.
- **ETF в UI**: прямой feedback и обучение пользователя значению доверия в сети — рекомендуем показывать ETF в реальном времени.
- **Явные ошибки TTL для пользователя**: повышение прозрачности, исключение эффекта «пропажи без вести»; даёт объяснимый пользовательский опыт.
- **Конфигурируемый лимит rate limiting**: допускает адаптацию под реальные сценарии — высокий rate для тестовых/малых сетей, жёсткий для публичных.

## 4. Рассмотренные альтернативы
- **Доверительная фильтрация или депозиты**: усложняют UX, требуют отдельной экономики, нетотально решают root-проблему спама.
- **Микс-сети, таймерные перемешивания**: очень сложны для реализации на распределённой P2P-сети, приводят к росту латентности и несопоставимы по издержкам с задачами первой версии.
- **Сокрытие ETF**: противоречит принципу обучения пользователя и принципу traceability сети.
- **Игнорировать TTL/ошибки доставки**: ведёт к неявным сбоям, нарушает прозрачность.
