# Feature Specification: Documentation Refactor v1.0.0

**Feature Branch**: `001-docs-refactor`  
**Created**: 2025-12-01  
**Status**: Draft  
**Input**: Refactor project documentation for version v1.0.0 to ensure full structural consistency, link integrity, and separation between human-readable documentation and AI-oriented specifications.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Repository Inventory & Coverage (Priority: P1)

Every Markdown file in the workspace is cataloged, version-tagged for v1.0.0, and tied to an index so reviewers can prove that documentation is complete.

**Why this priority**: Without full inventory coverage, later restructuring risks missing artifacts, leaving orphaned guidance that confuses contributors and AI agents.

**Independent Test**: Run the documentation inventory script to produce a manifest showing 100% of `.md` files (minus the excluded list) and cross-check that each entry links back to at least one index.

**Acceptance Scenarios**:

1. **Given** a fresh clone of the repo, **When** the inventory command runs, **Then** it lists every `.md` file along with its canonical section (README, `/docs`, or `/spec`) and v1.0.0 status flag.
2. **Given** an added Markdown file anywhere in the repo, **When** inventory is re-run, **Then** the new file appears in the manifest and is reported as “unlinked” until connected to an index.

---

### User Story 2 - Link Integrity & Reference Graph (Priority: P2)

Repository maintainers can click through Markdown paths starting from `[README.md](README.md)` without encountering dead links or unresolved references.

**Why this priority**: Link rot undermines trust in the docs and blocks Cursor agents that rely on deterministic navigation.

**Independent Test**: Execute automated link traversal beginning at `[README.md](README.md)`; fail the run if any Markdown hyperlink is invalid or if referenced files are missing version v1.0.0 headers.

**Acceptance Scenarios**:

1. **Given** the traversal starts at `[README.md](README.md)`, **When** it recursively follows Markdown links, **Then** every referenced file opens successfully and restates v1.0.0 context.
2. **Given** an `.md` file that is not referenced anywhere, **When** the final audit runs, **Then** it is reported and either linked from an index or archived intentionally.

---

### User Story 3 - Hierarchical Restructure & Content Separation (Priority: P3)

Readers see concise summaries at the root, detailed human documentation under `/docs`, and signal-rich AI specs under `/spec` without duplicate paragraphs.

**Why this priority**: Clear layering keeps README approachable while giving humans and AI distinct entry points tailored to their needs.

**Independent Test**: Review the new structure: README ≤400 words with section links, `/docs` hosting full narratives grouped by topic, and `/spec` containing condensed decision assets; no file repeats the same paragraph across directories.

**Acceptance Scenarios**:

1. **Given** the updated README, **When** a contributor scans it, **Then** they find high-level summaries plus links into `/docs` and `/spec` without deep-release notes inline.
2. **Given** a spec file under `/spec`, **When** auditors review it, **Then** they find only condensed, instruction-style content targeted at AI agents, referencing `/docs` for narrative depth.

### Edge Cases

- Files generated by automation (e.g., Spec-Kit outputs) should be inventoried but may remain unreferenced if intentionally archived—must flag and annotate rationale.
- References pointing to external URLs must still be validated; unreachable URLs should be logged with remediation notes instead of silently ignored.
- Large monolithic docs (e.g., >5k words) might need partitioning; ensure internal anchors or split files maintain version headers and backlinks.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Produce an authoritative Markdown inventory (path, relative section, version flag) covering 100% of `.md` files excluding `[CONTRIBUTING.md](CONTRIBUTING.md)`, `LICENSE.txt`, `[SECURITY.md](SECURITY.md)`, and `[CHANGELOG.md](CHANGELOG.md)`.
- **FR-002**: Convert every inline path reference (e.g., `[spec/01-product-vision.md](spec/01-product-vision.md)`) into a valid Markdown hyperlink pointing to an existing file.
- **FR-003**: Traverse links starting at `[README.md](README.md)`; create or update all referenced files so they exist, state v1.0.0 applicability, and are added to the processed list.
- **FR-004**: Identify unreferenced Markdown files after traversal and link each from an appropriate index (README, `[docs/README.md](docs/README.md)`, or `[spec/README.md](spec/README.md)`) or document why the file remains isolated.
- **FR-005**: Relocate verbose release or deep-dive sections from top-level files into structured `/docs` topics, leaving ≤400-word summaries plus links in each top-level file.
- **FR-006**: Ensure `/spec` contains only concise, AI-facing material; update `[spec/README.md](spec/README.md)` to instruct agents to default to `/spec` for planning while referencing `/docs` for narrative context.
- **FR-007**: Document the release-install choice matrix (CLI, Server, Desktop UI, Mobile) within README summaries and provide canonical links to the detailed `/docs` instructions.
- **FR-008**: Deliver an automated validation report (log or markdown) confirming zero dead links, zero duplicate paragraphs between `/docs` and `/spec`, and the pass/fail status of exclusion rules.

### Key Entities *(include if feature involves data)*

- **Documentation Node**: A Markdown file with attributes path, audience (`root`, `docs`, `spec`), version tags, and linkage status.
- **Reference Graph**: Directed edges captured during traversal, recording source file, hyperlink text, and target path/URL, used to detect broken or missing links.
- **Index Gateway**: Entry documents (`[README.md](README.md)`, `[docs/README.md](docs/README.md)`, `[spec/README.md](spec/README.md)`) responsible for linking every Documentation Node either directly or through topic hierarchies.

## Dependencies & Assumptions

- Spec-Kit automation (`scripts/doc_refactor` and `/speckit.*` flows) remains available to generate inventories, prompts, and validation reports.
- `[CONTRIBUTING.md](CONTRIBUTING.md)`, `LICENSE.txt`, `[SECURITY.md](SECURITY.md)`, and `[CHANGELOG.md](CHANGELOG.md)` stay authoritative; this effort only adjusts links pointing to them, not their body content.
- README summaries can reference detailed `/docs` sections because those files exist or will be created during this effort.
- Release automation (v1.0.0) already defines CLI, Server, Desktop, and Mobile installer flows; this feature only reorganizes how those instructions are presented.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Documentation inventory reports 100% of `.md` files (exclusions noted) with validated locations and v1.0.0 status.
- **SC-002**: Automated link traversal completes with 0 broken internal Markdown links and <1% external link warnings (all warnings logged with rationale).
- **SC-003**: Top-level README is ≤400 words, lists all four release surfaces, and links to corresponding `/docs` sections; `/docs` houses all detailed release notes.
- **SC-004**: `[spec/README.md](spec/README.md)` explicitly directs AI agents to rely on `/spec` first, and each spec file references the matching `/docs` topic without duplicating paragraphs—verified by diff or lint output documenting 0 duplicated blocks.
